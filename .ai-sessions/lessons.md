- A live-Temporal "hang" that prints "signal fd N write failed (Bad file descriptor)" is NOT necessarily a bridge signal-fd / fork-pool / CLOEXEC bug — that line is BENIGN teardown-race noise printed AFTER the await already failed, during runtime/callback teardown. It misled three investigators on #1 (sync-activity). Before writing an SDK fd fix, FALSIFY the premise: (a) reproduce the activity IN-PROCESS with NO fork — if it fails the same way, no fork-pool FD sweep can be the cause; (b) `dup`-probe the parent's signal fd every tick — if it stays open, nothing closed/corrupted it; (c) run a CORRECT sync `:Defn(...,'sync=1')` activity live through the fork pool — if it returns its value, the path is healthy; (d) check the eventfd is already `EFD_CLOEXEC`. #1's real cause was a samples-perl import bug, not the SDK. UNDER `feature 'class'`, `use Foo qw(bar)` at FILE scope imports `bar` into the file's `package main`, NOT into a later `class Some::Class { ... }` block — so an unqualified `bar(...)` inside the class resolves to an undefined `Some::Class::bar` and dies on every call; an unlimited-retry activity then loops ~200s and looks like a worker hang. Fix the call site (qualify or import into the class's own package), not the SDK (2026-06-26)

- IO::Async installs ONE process-wide SIGCHLD reaper the first time ANY child is watched (`IO::Async::Loop::watch_process`, triggered when the sync-activity `IO::Async::Function` fork pool forks its first worker); its `_reap_children` does `waitpid(-1, WNOHANG)` and reaps EVERY exited child, and it LINGERS for the loop's life (only `unwatch_process` detaches it — reaping a child via the SIGCHLD path does NOT). This SEGVs sdk-core at teardown (#1, exit 139 / signal 11, ONLY when a sync fork-pool activity ran earlier in the process): the ephemeral `Temporalio::Test::DevServer` makes sdk-core spawn + `waitpid()` its own `temporal` CLI subprocess, and IO::Async's reaper wins the `waitpid(-1)` race and reaps it first, so core's own `waitpid` crashes. It is NOT a signal-fd/CLOEXEC bug (that B0 hypothesis was disproven by experiment) and NOT fixed by `local $SIG{CHLD}='DEFAULT'` (IO::Async installs the handler below `%SIG`). FIX is test-teardown-side in `Temporalio::Test::DevServer->shutdown`: for the core-shutdown window, detach the loop's childwatch CHLD handler (`my $sigid = delete $loop->{childwatch_sigid}; $loop->detach_signal('CHLD',$sigid)`) so core reaps its own child, and reap any STILL-watched stopped fork-pool worker yourself (`waitpid($pid, WNOHANG)` over `keys %{$loop->{childwatches}}`, then reset it to `{}`) to avoid a zombie — `IO::Async::Function->stop` is async and leaves one worker watched-but-unreaped at teardown, so an "only suspend when childwatches empty" guard stays RED. IO::Async lazily re-arms the handler on its next `watch_process`. Production is unaffected (a worker against an external server never runs the ephemeral-server shutdown). DIAGNOSE a teardown-order race by printing the loop's `childwatches`/`childwatch_sigid` at the race point before writing the fix — the live state contradicted the assumed "worker shutdown already reaped the pool" order. No shim/cargo/Callback.pm change (2026-06-26)
- For a live Temporal bug whose failure mode is a HANG (not a wrong value) — e.g. a raw-cancel that fails the workflow task forever (#5) or a client cancel mid-:Update that wedges ~183s (#8) — the durable repro is SUBPROCESS-GUARDED, not in-process: a naive in-process repro hangs the whole `prove` run. `t/lib/SubprocessGuard.pm::run_guarded($child_code, timeout => 30)` forks a child that runs the ENTIRE worker+cancel scenario and exits 0 ONLY on a verified-clean outcome, while the parent reaps it under a hard timeout and reports a clean fail on overrun. FOUR load-bearing details: (1) create the `Temporalio::Runtime` INSIDE the child — fork() after sdk-core's Tokio threads start is unsafe; the parent only `require`s modules (attaching FFI symbols starts no threads) and forks BEFORE any `->new`. (2) child calls `POSIX::setsid` so it is its own process-group leader; the parent kills the whole group with `kill 'TERM'/'KILL', -$pid` on overrun, which reaps the dev-server CLI that sdk-core spawned (otherwise it orphans). (3) child leaves via `POSIX::_exit` — NOT `exit`/die-to-top — so no END/Test2 done_testing handler fires in the forked copy and corrupts the parent's TAP stream; the child touches ZERO Test2 functions, the PARENT owns the one assertion. (4) the parent polls `waitpid($pid, WNOHANG)` in a `Time::HiRes::sleep(0.2)` loop until a deadline rather than blocking, so the timeout is enforced even if the child wedges. RED is then "child trips the 30s timeout / exits non-zero", GREEN is "child exits 0 in 3-4s"; the same pattern serves every SUBPROCESS-GUARDED live repro (B4-B6). Reuse `t/lib/SubprocessGuard.pm`, do not re-derive (2026-06-26)

## Async
- `Future->call` and `Future->wrap` are NOT interchangeable for "run user code that may be sync or async": `Future->call(BLOCK)` runs BLOCK and REQUIRES it to return a Future — a plain (non-Future) return dies "Expected ... to return a Future". So `Future->call(sub { $code->(@args) })` works for a body that returns a Future or throws, but breaks for a sync body returning a plain value (the die is caught and surfaces as a FAILED completion, e.g. an activity the server then redelivers forever). The robust idiom is `Future->call(sub { Future->wrap($code->(@args)) })`: `Future->wrap` passes a returned Future through unchanged and normalises a plain value/list into a done Future, while `Future->call` still routes a synchronous die into a failed Future (2026-06-13)
- Per-level methods generated via typeglob assignment (`*{"Class::$level"} = sub {...}`) inside a `feature 'class'` block CANNOT close over `field` variables — they are plain file-scope subs, not methods, so `$logger` (a field) errors "Field is not accessible outside a method" at compile. Route the installed closures through a public `method` accessor (`$self->base_logger->$level(...)`); the only field visible from such a sub is via `$self`. Used to generate the replay-aware workflow logger's level surface (2026-06-13)
- A continue-as-new / control-flow signal raised from workflow code to unwind `:Run` must NOT be a `Temporalio::Exception` subclass: the completion-outcome decision table treats any `Temporalio::Exception::*` escaping the body as a Temporal failure (-> FailWorkflowExecution), so a continue-as-new modeled as one is misrouted as a workflow failure. Model it as a PLAIN blessed object identified by class and caught BEFORE the failure branch (mirrors sdk-python `_ContinueAsNewError` caught before the generic Exception handler). Branch ORDER in the table is load-bearing: continue-as-new first, then Cancelled-gated-on-cancel_requested, then is-failure-exception, then task-fail (2026-06-13)
- A cancellable workflow awaitable backed by a CPAN Future must NOT model cancellation as Future's native `->cancel`: that transitions the future to the cancelled state and fires `on_cancel` callbacks AFTER it is already ready, so an in-callback `$f->fail(Cancelled)` is a silent no-op and `await $f` throws a bare "<obj> was cancelled" STRING — losing the `Temporalio::Exception::Cancelled` identity the body catches. Instead use a Future SUBCLASS that OVERRIDES `cancel` to (a) run the command-emitting callback and (b) `->fail` with the proper Temporal exception, never entering the native cancelled state. The reference SDKs all raise a cancellation EXCEPTION into the awaiting frame (sdk-ruby `fiber.raise(CanceledError)`, sdk-python task-cancel -> `CancelledError`); the exception class is load-bearing. Reuse this shape for activity cancel (P3.7), wait_condition timeout, and child-workflow cancel (2026-06-13)

## Architecture
- Workflow determinism guard (P10.8, spec §29.4, NARROWED M2) is process-global `CORE::GLOBAL::` overrides of the TIME/ENTROPY surface ONLY - `time`/`localtime`/`gmtime`/`rand`/`srand`/`sleep` plus symbol-table overrides of `Time::HiRes::{time,gettimeofday,sleep}`; deliberately NOT `open`/`fork`/`system`/etc (those would trap IO::Async + the sync-activity fork pool, which share the main thread where `$Runner::CURRENT` is set). Each override: `_trap if defined $Runner::CURRENT && $SUPPRESS_DEPTH==0` else `goto`/delegate to `CORE::builtin`. THREE concrete gotchas: (1) under `use v5.38` the `(...)` after `sub` is a SIGNATURE, not a prototype, so a CORE::GLOBAL override written `sub (;$)` is a syntax error and `sub ()` mis-declares - put `no feature 'signatures'` in the guard file and use classic prototypes + `@_`. (2) `Scalar::Util::set_prototype` has a `(&$)` prototype and REJECTS a variable arg ("must be block or sub {}"), so you can't copy a prototype dynamically - hardcode the Time::HiRes overrides as literal `sub ()` / `sub (;@)` to match what Time::HiRes ships and kill the "Prototype mismatch" redefine warnings. (3) a Nondeterminism THROWN from the body (not recorded via `_record_nondeterminism`) escapes `:Run` and isa `Temporalio::Exception`, so the generic `_outcome_for_failure` branch fails the WORKFLOW - add an explicit Nondeterminism branch BEFORE `_is_workflow_failure_exception` that routes task-vs-workflow-fail on `nondeterminism_as_workflow_fail` (same as a recorded one). Escape hatch is `Unsafe::illegal_call_tracing_disabled(&)` raising `$DeterminismGuard::SUPPRESS_DEPTH` via `dynamically` (NEVER `local`). Guard is default-ON; `disable_determinism_guard` worker kwarg just skips the (idempotent) install. T-det-7 pins the documented gap: `CORE::time` is NOT trapped (CORE::-qualified calls bind the builtin directly), neither are IO builtins. ASCII em-dashes in a Test2 message string cause a real "Wide character in print" warning under `use utf8` - scrub them (2026-06-25)
- Worker deployment versioning (P10.5, spec §29.1) has THREE gotchas. - Interceptor framework (spec §27, P10.1) is four `:isa`/`feature 'class'` base-class surfaces whose default methods delegate to `$self->next->$method($_[0])`: Client `OutboundInterceptor` (start_workflow/signal_with_start_workflow/signal_workflow/query_workflow/start_workflow_update), Worker `ActivityInbound` (init/execute_activity), `WorkflowInbound` (init/execute_workflow/handle_signal/handle_query/validate_update/handle_update), `WorkflowOutbound`. `intercept_client`/`intercept_activity`/`intercept_workflow` return the wrapped instance (Ruby shape). - M1 completion gating is WARN-AND-COMPLETE, not hard-block (spec §19.2 corrected; parity with sdk-python `_warn_if_unfinished_handlers` + sdk-ruby): when `:Run` returns with a handler still in `%in_progress_handlers`, `_build_completion` WARNS and completes (abandoning the handler) rather than withholding CompleteWorkflowExecution. - A buffered workflow command (e.g. a child-cancel) is DISCARDED if the same activation ends in a workflow FAILURE: `_workflow_failed_completion` does `@commands = (fail_workflow_execution(...))`, REPLACING the buffer (parity with sdk-python — a failing workflow emits only the FailWorkflowExecution command). So `$handle->cancel` immediately followed by an `await $handle->result` that raises a Temporal failure in the SAME activation loses the CancelChildWorkflowExecution. Design cancel scenarios across SEPARATE activations (emit the cancel, then settle the result on a later activation's resolve job). - Child-workflow cancellation_type splits `$handle->cancel` behaviour (spec section 18.2, ChildWorkflowCancellationType proto): abandon(0) emits NO command + stops waiting now; try_cancel(1) emits the command + reports cancellation now; wait_cancellation_completed(2)/wait_cancellation_requested(3) emit the command but STAY PARKED on `result` until the later cancelled resolve. A whole-workflow `CancelWorkflow` job is DIFFERENT — it cancels the primary task, so it fails the pending child awaits REGARDLESS of cancellation_type (mirrors the activity cancel chain / T-act-9). Guard the cancel-command emission with a per-handle `$cancel_emitted` flag since both `$handle->cancel` and `_apply_cancel_workflow` can fire it (2026-06-23)
- A child workflow's two-stage resolution (StartChildWorkflowExecution -> ResolveChildWorkflowExecutionStart THEN ResolveChildWorkflowExecution) needs a handle wrapping TWO Futures in `%pending_child_workflows{$seq}`: start-success ->dones the START future (and keeps the seq mapped — the result job still comes); start-failed/cancelled pops the seq and fails the START future; the terminal resolve pops the seq and settles the RESULT future. `start_child_workflow`/`execute_child_workflow` are BOTH async (await the start), unlike `start_activity` which returns its Future synchronously. To emit two children's start commands in ONE activation, issue both async calls before awaiting either (each runs to its first await, emitting its command). MUST-match proto names: command field is `input` not `arguments`, reuse is `workflow_id_reuse_policy`, cancel keys on `child_workflow_seq` not `seq` (2026-06-23)
- A LEGACY QUERY (sdk-core `LEGACY_QUERY_ID = "legacy_query"`) is delivered on its own workflow task; Core replays history to rebuild state, then expects the lang SDK to answer ONLY the query. If your completion carries the legacy-query QueryResult alongside ANY other command, Core REJECTS it ("Workflow completion had a legacy query response along with other commands", sdk-rust `worker/workflow/mod.rs:1264`) and the worker dies. Two complementary runner fixes: (1) gate the wait_condition re-check by job-set index — `_pump(check_conditions => $set_index==1||$set_index==2)`, matching sdk-python `activate()` `_run_once(check_conditions=index==1 or 2)`, so a query set (3) never advances the body; (2) in `_successful_completion`, when the buffer contains a "legacy_query" RespondToQuery, filter the buffer down to ONLY query-response commands (the body's commands were already in history). This path is reachable ONLY live — the replay suite never triggers it, so the integration gate is load-bearing (2026-06-13)
- A workflow `:Signal`/`:Query`/`:Update` handler is a METHOD, so it cannot run until the runner's `_apply_initialize` has created the instance — even though the handler DEFINITION exists at class-compile time (unlike sdk-python, where `self._signals` is populated in `__init__` before the primary task). Combined with the de-facto job ordering (signals are job set 1, applied BEFORE InitializeWorkflow in set 2), this forces a buffer-then-drain flow: `_apply_signal_workflow` buffers any signal arriving while `$instance` is undef (or with no matching named/dynamic handler) into `%buffered_signals{name}`, and `_apply_initialize` calls `_drain_buffered_signals` right after instantiating the class. This is what makes T-wf-3 work (a signal in the init activation is visible to the `:Run` continuation). An unhandled signal stays buffered indefinitely in the static model — it never fails the workflow (2026-06-13)
- An async `:Signal` handler must be tracked so the workflow is not considered complete while it is in-flight (spec section 10.3 / sdk-python `_in_progress_signals` + `workflow_all_handlers_finished`): dispatch it via `Future->call(sub { Future->wrap($instance->$h(@args)) })`, and if the resulting Future is NOT already ready, store it in `%in_progress_handlers{++$seq}` with an `on_ready` that deletes the entry. `_build_completion` then withholds CompleteWorkflowExecution (emits only the activation's buffered commands) while any handler Future is pending, even if `:Run` already returned. `evict` must also cancel these handler Futures (2026-06-13)
- The workflow Runner has TWO field lifetimes and conflating them double-emits commands: WORKFLOW-scoped state (the seq counter, the pending-Futures map, the instance, the RNG, run_id) persists across every activation for the run; ACTIVATION-scoped state (the outbound command buffer, is_replaying, the activation timestamp) must be RESET at the top of each `process_activation` because the worker returns one completion per activation. Symptom of getting it wrong: a later activation's completion still carries a prior activation's `ScheduleActivity` (e.g. 2 commands when the test expects 1). When adding a new runner field, classify its lifetime explicitly (2026-06-13)

## Perl
- Future::AsyncAwait + `feature 'class'` parser footgun (5.38.2): once `use Future::AsyncAwait` is active in a compilation unit, a `field $x :param[= default]` declared ALONGSIDE a SIGNATURED method (`method foo ($a) {...}`) silently POISONS the parser for EVERY class that follows in the same file — the failure surfaces as "Subroutine attributes must come before the signature" on the NEXT class, NOT on the offending one. Two robust workarounds, both used in P10.1: (1) keep ONE such class per file (e.g. `Client/_RootOutbound.pm` got its own file because `Temporalio::Client` precedes it), or (2) make the later classes' methods SIGNATURE-LESS and read args from `@_` (`method foo { my ($a)=@_; ... }`) — sig-less methods sit fine next to `:param` defaults (matches Nexus/OperationContext's accessor style). SEPARATELY: in a TEST file, a `feature 'class'` block disables the bareword Test2 exports for everything after it, so call Test2 helpers via the `T2->` package form (`T2->subtest('n' => sub {...})`, `T2->is(...)`, `T2->like(T2->dies(sub{...}), qr/../, 'd')`) — same idiom as t/unit/activity_dispatch.t. ## FFI / Shim
- Custom metric meters (P10.4, spec §28.2) have TWO non-obvious crash sources, both nondeterministic SEGVs. (1) The spec spike says "run the Perl method INLINE on the main thread to avoid self-deadlock" — DO NOT implement that by having the Rust shim call a Perl FFI::Platypus closure synchronously from inside a callback: that callback is itself reached through an FFI call, and libffi corrupts on the SECOND nested FFI-closure re-entry (the crash surfaces on the NEXT FFI call, e.g. shutdown, not the closure). Resolve it by making the marshalled callbacks (`metric_new`/`attributes_new`/`*_free`) ALLOCATE THE HANDLE ID IN THE SHIM, park a request on a `VecDeque<MeterRequest>`, and RETURN THE ID IMMEDIATELY — never block, never call Perl from a callback. The main-thread drain (Callback.pm, after the completion-queue drain) pops parked requests, runs the Perl method, binds the shim id in `%METRIC`/`%ATTRIBUTES`, then pulls aggregated record buckets. `record_*` aggregate in PURE RUST (`HashMap<(metric_id,attrs_id),(kind,sum,count)>`) on the calling Tokio thread, zero Perl contact (T-meter-7: 8 threads x 1000 sums exactly). Thread-agnostic, so the spike is satisfied by construction. (2) Core RETAINS the `TemporalCoreCustomMetricMeter` struct BY POINTER for the runtime's lifetime (header: "freed by a callback within itself"), so Runtime's `@keep` (which pins the 8-pointer `CustomMetricMeter` record) MUST be promoted to a field (`$telemetry_keep`) when a meter is configured — dropping it right after `runtime_new` leaves core a dangling pointer and a nondeterministic crash even with NO metric_new.
