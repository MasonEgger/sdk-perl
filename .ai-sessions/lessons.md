# Lessons Learned

## Recent
<!-- 10 most recent lessons, newest first -->
- When a TDD "set the value" step (e.g. version-agreement, config invariant) lands on a tree where earlier commits ALREADY set the values correctly, do NOT manufacture a fake-wrong tree to get a RED run. Write the guard test, then DEMONSTRATE it bites by perturbing one input on disk, confirming the assertion fails (non-zero exit), and REVERTING immediately — back up the file first (`cp X /tmp/X.bak`) and restore from the backup, then re-run to confirm green and `git status` clean. The guard ships green; RED is proven, not staged. Faithful TDD discipline without a dishonest commit (2026-06-13)
- A multi-distribution monorepo has TWO independent version axes that must not be conflated in an agreement test: the Perl DIST version (the three `dist.ini` + `our $VERSION` + the shim `Cargo.toml`, all at the release cadence, `0.1.0`) versus the Alien UPSTREAM version (`Alien::Temporalio::Core->version` = `runtime_prop->{version}` derived from the alienfile `$pinned_tag` `v0.4.0` -> `0.4.0`), which tracks the vendored sdk-core release. The agreement test must assert the dist axis is internally consistent AND that the upstream pin is DISTINCT from it (a guard against accidentally syncing them) (2026-06-13)
- POD coverage on a `feature 'class'` SDK: drive the work from `Pod::Coverage::CountParents->naked` (the authoritative per-package list of undocumented public subs) — `pod_coverage_ok` auto-PASSes packages with no public symbols (pure-POD entry modules, underscore-named private classes), so no special-casing needed. `method NAME { $NAME }` field readers are documentable with an accurate one-liner; only the substantive minority need hand-written prose. For generated/internal sub families (the raw C-ABI bindings in `Core::FFI`, the looped Log::Any level methods in `Workflow::Logger`), document them collectively in prose and put a regex in the TEST's `trustme` table — do NOT rely on `=for Pod::Coverage` in the .pm: Pod::Coverage did not honor those directives here even with blank-line-separated paragraphs. Also: `=encoding utf8` MUST be the first POD directive (place it right before `=head1 NAME`) or Test::Pod fails every file whose POD contains an em-dash (2026-06-13)
- Transient gRPC RETRY for client RPCs (incl. `result()`'s long-poll) is owned by sdk-CORE, NOT by Perl: there is NO Perl-level retry loop in `WorkflowHandle::result` or the history-event iterator. Every poll funnels through `Client->_rpc_call` with the default `retry => 1`, and core applies the client RetryConfig to absorb transient UNAVAILABLE/RESOURCE_EXHAUSTED/DEADLINE_EXCEEDED (spec §7.5/§7.6 point 3). Consequence for tests: do NOT inject a transient RpcError into `_rpc_call` and expect `result()` to retry — Perl will surface it as a hard failure. The correct, faithful assertion for "transient retried transparently" (T-cli-result-5) is to spy on `_rpc_call` and assert every result long-poll `GetWorkflowExecutionHistory` carries `retry => 1` (so core retries), then let the real call resolve. Check "who owns the retry" before writing any retry-resilience test (2026-06-13)
- LIVE cancellation timing differs by the workflow's PARK POINT: a `temporal server start-dev` delivers the `CancelWorkflow` task PROMPTLY when the workflow is parked on a TIMER (a pure-timer workflow cancelled at 1.5s ended Cancelled with ~0s result wait), but BATCHES `CancelWorkflow` behind an in-flight ACTIVITY's resolution — the worker never sees a standalone cancel activation while an activity is pending; it arrives in one job-set-2 activation alongside that activity's `ResolveActivity` only once the activity completes (so a workflow that just `await`s a long activity can finish normally before the cancel takes effect). For deterministic LIVE cancel tests, park the workflow on a long timer; prove the activity-level cancel-chain COMMANDS (RequestCancelActivity emission + abandon suppression) in the replay suite, not live. To diagnose such batching, temporarily `warn` the activation's job-variant list + is_replaying at the top of `process_activation` (2026-06-13)
- A LEGACY QUERY (sdk-core `LEGACY_QUERY_ID = "legacy_query"`) is delivered on its own workflow task; Core replays history to rebuild state, then expects the lang SDK to answer ONLY the query. If your completion carries the legacy-query QueryResult alongside ANY other command, Core REJECTS it ("Workflow completion had a legacy query response along with other commands", sdk-rust `worker/workflow/mod.rs:1264`) and the worker dies. Two complementary runner fixes: (1) gate the wait_condition re-check by job-set index — `_pump(check_conditions => $set_index==1||$set_index==2)`, matching sdk-python `activate()` `_run_once(check_conditions=index==1 or 2)`, so a query set (3) never advances the body; (2) in `_successful_completion`, when the buffer contains a "legacy_query" RespondToQuery, filter the buffer down to ONLY query-response commands (the body's commands were already in history). This path is reachable ONLY live — the replay suite never triggers it, so the integration gate is load-bearing (2026-06-13)
- A workflow `:Signal`/`:Query`/`:Update` handler is a METHOD, so it cannot run until the runner's `_apply_initialize` has created the instance — even though the handler DEFINITION exists at class-compile time (unlike sdk-python, where `self._signals` is populated in `__init__` before the primary task). Combined with the de-facto job ordering (signals are job set 1, applied BEFORE InitializeWorkflow in set 2), this forces a buffer-then-drain flow: `_apply_signal_workflow` buffers any signal arriving while `$instance` is undef (or with no matching named/dynamic handler) into `%buffered_signals{name}`, and `_apply_initialize` calls `_drain_buffered_signals` right after instantiating the class. This is what makes T-wf-3 work (a signal in the init activation is visible to the `:Run` continuation). An unhandled signal stays buffered indefinitely in the static model — it never fails the workflow (2026-06-13)
- An async `:Signal` handler must be tracked so the workflow is not considered complete while it is in-flight (spec section 10.3 / sdk-python `_in_progress_signals` + `workflow_all_handlers_finished`): dispatch it via `Future->call(sub { Future->wrap($instance->$h(@args)) })`, and if the resulting Future is NOT already ready, store it in `%in_progress_handlers{++$seq}` with an `on_ready` that deletes the entry. `_build_completion` then withholds CompleteWorkflowExecution (emits only the activation's buffered commands) while any handler Future is pending, even if `:Run` already returned. `evict` must also cancel these handler Futures (2026-06-13)
- `Future->call` and `Future->wrap` are NOT interchangeable for "run user code that may be sync or async": `Future->call(BLOCK)` runs BLOCK and REQUIRES it to return a Future — a plain (non-Future) return dies "Expected ... to return a Future". So `Future->call(sub { $code->(@args) })` works for a body that returns a Future or throws, but breaks for a sync body returning a plain value (the die is caught and surfaces as a FAILED completion, e.g. an activity the server then redelivers forever). The robust idiom is `Future->call(sub { Future->wrap($code->(@args)) })`: `Future->wrap` passes a returned Future through unchanged and normalises a plain value/list into a done Future, while `Future->call` still routes a synchronous die into a failed Future (2026-06-13)
- Per-level methods generated via typeglob assignment (`*{"Class::$level"} = sub {...}`) inside a `feature 'class'` block CANNOT close over `field` variables — they are plain file-scope subs, not methods, so `$logger` (a field) errors "Field is not accessible outside a method" at compile. Route the installed closures through a public `method` accessor (`$self->base_logger->$level(...)`); the only field visible from such a sub is via `$self`. Used to generate the replay-aware workflow logger's level surface (2026-06-13)
- A continue-as-new / control-flow signal raised from workflow code to unwind `:Run` must NOT be a `Temporalio::Exception` subclass: the completion-outcome decision table treats any `Temporalio::Exception::*` escaping the body as a Temporal failure (-> FailWorkflowExecution), so a continue-as-new modeled as one is misrouted as a workflow failure. Model it as a PLAIN blessed object identified by class and caught BEFORE the failure branch (mirrors sdk-python `_ContinueAsNewError` caught before the generic Exception handler). Branch ORDER in the table is load-bearing: continue-as-new first, then Cancelled-gated-on-cancel_requested, then is-failure-exception, then task-fail (2026-06-13)
- A cancellable workflow awaitable backed by a CPAN Future must NOT model cancellation as Future's native `->cancel`: that transitions the future to the cancelled state and fires `on_cancel` callbacks AFTER it is already ready, so an in-callback `$f->fail(Cancelled)` is a silent no-op and `await $f` throws a bare "<obj> was cancelled" STRING — losing the `Temporalio::Exception::Cancelled` identity the body catches. Instead use a Future SUBCLASS that OVERRIDES `cancel` to (a) run the command-emitting callback and (b) `->fail` with the proper Temporal exception, never entering the native cancelled state. The reference SDKs all raise a cancellation EXCEPTION into the awaiting frame (sdk-ruby `fiber.raise(CanceledError)`, sdk-python task-cancel -> `CancelledError`); the exception class is load-bearing. Reuse this shape for activity cancel (P3.7), wait_condition timeout, and child-workflow cancel (2026-06-13)

## Architecture
- The workflow Runner has TWO field lifetimes and conflating them double-emits commands: WORKFLOW-scoped state (the seq counter, the pending-Futures map, the instance, the RNG, run_id) persists across every activation for the run; ACTIVATION-scoped state (the outbound command buffer, is_replaying, the activation timestamp) must be RESET at the top of each `process_activation` because the worker returns one completion per activation. Symptom of getting it wrong: a later activation's completion still carries a prior activation's `ScheduleActivity` (e.g. 2 commands when the test expects 1). When adding a new runner field, classify its lifetime explicitly (2026-06-13)

## Workflow
- The C bridge header declares shapes, but the bridge's .rs conversion code declares semantics (empty-string traps, free-after-callback ordering, stdio inheritance) — read both before writing FFI wrappers (2026-06-12)
- For sdk-core async lifecycle calls, read the CORE `.rs` method (not just the bridge) to learn what it awaits: `worker_finalize_shutdown` → `Worker::shutdown` blocks on `workflows.shutdown()` until the poll loop returns ShutDown, so a never-run worker deadlocks on finalize — initiate+free only until `run` drives the loops (2026-06-13)
- Verify MUST-match wire constants (payload encodings, gRPC code maps, defaults) by grepping the reference SDK source yourself — Explore subagents paraphrase (reported "json/proto"; actual constant is "json/protobuf") (2026-06-10)
- Sibling reference checkouts track upstream HEAD and can drift from spec MUST-match constants (sdk-rust RetryOptions multiplier 1.5→1.7) — on disagreement, confirm against a second reference SDK; spec wins (2026-06-12)
- Read the actual sdk-core C bridge header before specing or planning FFI work — it alone revealed by-value tagged unions in WorkerOptions and the absence of a buffered-metrics API (2026-06-10)
- Cross-check new-SDK semantics against at least two reference SDKs (Python for workflow semantics, Ruby for worker architecture) — single-source review missed RemoveFromCache eviction and the cancel-vs-fail completion command (2026-06-10)
- When a parallel tool batch partially fails (e.g. classifier outage), re-dispatch only the cancelled calls — results from the surviving calls in the batch remain valid (2026-06-10)
- To write files larger than one response allows, end each chunk with a unique marker comment and append via Edit on the marker (2026-06-10)

## Protobuf
- Generated Protobuf message accessors (Temporalio::Proto::*) are READ-ONLY — `$msg->field($x)` silently no-ops (no error), so build every field via `Class->new(\%fields)`; collect variant-only fields (e.g. SignalWithStart's signal_name/signal_input) into an extras hash and merge into the constructor args rather than setting them after construction (2026-06-12)
- A generated proto built via `Class->new({ nested => { ... } })` leaves NESTED sub-messages as plain HASHREFS — they have no accessor methods and no `which_variant`, so `$msg->jobs->[0]->which_variant` (or `$completion->successful->commands`) dies "on unblessed reference". Round-trip through `Class->decode($msg->encode)` to materialize the fully-blessed proto the worker actually receives off the wire BEFORE walking its sub-messages. The replay harness does this on BOTH the inbound activation and the outbound completion; the WorkflowDispatcher must likewise round-trip the Runner-built completion before its codec-encode walk (2026-06-13)
- Messages delivered only inside a google.protobuf.Any (google.rpc.Status, temporal.api.errordetails.v1.*) are never imported by the service protos, so import-driven schema loading misses them — parse them as explicit roots; sdk-rust vendors google/rpc in a standalone proto root outside api_upstream (2026-06-12)

## Rust
- cbindgen renders opaque `_private: [u8; 0]` structs as zero-size definitions; borrowed foreign types need `[export] exclude` + `after_includes` forward typedefs to coexist with the owning header (2026-06-11)

## Perl
- Perl native `*` promotes to a DOUBLE once the product exceeds 2**53, silently dropping the low bits — so a 64-bit modular multiply (SplitMix64/PCG-style PRNGs) produces garbage (observed: constant 0xFFFFFFFE output for every seed). For deterministic integer generators use SHIFT/XOR-only algorithms (xorshift), which are exact in native Perl ints; reserve multiply-based mixers for `use integer` (signed modular) or an explicit 32x32->64 split (2026-06-13)
- `our $VAR` in a file with NO leading `package` statement lands in whatever the ambient package is (usually `main::`), NOT in the class the file defines — so a `feature 'class' { ... }` module whose package var is read elsewhere as `$The::Class::VAR` silently reads undef. Declare it inside an explicit `package The::Class { our $VAR; }` block and reference it fully-qualified in the `dynamically`/assignment (2026-06-13)
- A `die`/`->throw` that escapes a BEGIN-phase `:ATTR(CODE,BEGIN)` attribute handler during `require` is STRINGIFIED by the Perl compiler ("<msg>BEGIN failed--compilation aborted at ...") — the blessed exception object does NOT survive across the require boundary, so `blessed($@)` is false and `$@->isa(...)` cannot be tested. For compile-time attribute-validation (duplicate `:Run`/`:Signal` etc.), the durable testable contract is the MESSAGE text; assert the blessed exception class only on a RUNTIME path (e.g. the registry constructor that re-validates). Make handler messages distinctive enough to `like`-match (2026-06-13)
- IO::Async::Function's fork worker RENUMBERS and closes spare fds in the child: a parent-side pipe whose write fd you inherit at fork is EBADF in the worker (low fd numbers get reused — fd 3 became an unrelated open file handle). So a LIVE child->parent side-channel pipe does not work for sync-activity heartbeat relay; instead collect heartbeat frames in the child and return them with the result, letting the PARENT relay each to the real FFI call (sdk-python uses a multiprocessing.Manager queue/separate process for the same reason). Corollary: close inherited parent FDs (FD hygiene) BY FILEHANDLE (`close($fh)` closes the right kernel fd regardless of renumbering), never by a bare fd number; and TEST fd hygiene by asserting the parent's KERNEL OBJECT is gone (probe `/proc/self/fd/N` no longer points at `anon_inode:[eventfd]`), not by "read fd N fails EBADF" which fd-reuse defeats (2026-06-13)
- A sync activity body running in a forked child uses `local $...::Context::CURRENT = $ctx` (NOT `dynamically`): the child body is synchronous, no `await` crosses it, so `local` is correct and Syntax::Keyword::Dynamically is unnecessary there — `dynamically` is only required on the async main-loop dispatch path where an await suspends/resumes and must restore the scope (2026-06-13)
- `feature 'class'` only generates a NAMED-param constructor (no BUILDARGS), so a spec-mandated positional `->new(\@x)` needs a glob wrapper: capture `Class->can('new')`, then `*Class::new = sub ($c,$arg){ ...validate...; $gen->($c, field => $arg) }` after the `class {}` block (`no warnings 'redefine'`) (2026-06-12)
- Scoping a dynamic var across a Future::AsyncAwait body with `dynamically $X = $v` must wrap the `await` itself, not just the synchronous call that produces the Future — `do { dynamically $X = $v; await $f }`, never `await do { dynamically $X = $v; build_future() }`; the latter unwinds the scope before the body runs/parks. The dispatcher that scopes Activity::Context::CURRENT must also `use Temporalio::Activity ()` so bodies can call `Temporalio::Activity::context()` (2026-06-13)
- A bare `class` file (no preceding `package` statement) compiles file-scope subs into `main::`, so calls from inside the class block fail with "Undefined subroutine &Class::_helper" — define every helper sub INSIDE the `class { }` block (2026-06-12)
- A lazy `state $x = eval { require Foo; 1 } ? 1 : 0` probe re-raises its failed `require` when the FIRST call lands inside a Future::AsyncAwait async frame (the async error-detection sees the leftover $@) — compute load-detection at module load time in a `my $HAVE_FOO = do { local $@; eval {...} }` instead of lazily per-call (2026-06-12)
- With Future::AsyncAwait loaded (0.71, perl 5.38.2), only ONE `class X :isa(Y)` declaration parses per file (the next gets leaked attribute-parser state) — one `:isa` class per file; subclasses can return `Future->done/fail` directly instead of `async` sugar (2026-06-12)
- Hand-pack C tagged unions as `pack('L x4', $tag) . $variant` zero-padded to the union size (largest member); validate every offset via a shim echo function over #[repr(C)] mirror structs copied from the owning crate (2026-06-11)
- Linux::FD::Event flags use long literals (`'non-blocking'`, `'close-on-exec'`) — spec §4.2's `'nonblock'` sketch is rejected; spike CPAN flag literals before coding against spec sketches (2026-06-11)
- FFI::Platypus `record(Class)` is by value (returns included), `record(Class)*` by pointer; FFI::Platypus::Record cannot nest records — flatten embedded structs to layout-identical fields (2026-06-11)
- FFI::Platypus::Record drops C trailing padding but inserts interior padding correctly — record sizeof is a valid array stride iff the final member ends max-aligned (probe with sentinel bytes first); read struct fields from an opaque ptr via `cast('opaque' => 'record(Class)*', $ptr)` (2026-06-12)
- A bare `class` file (no `package` statement) puts file-scope subs in `main::` — helper subs callable from inside the class must be defined inside the `class { }` block (2026-06-12)
- Alien::Build runs alienfiles via `do '<abs path>'` (`__FILE__` is real — usable to locate in-tree sources); Test::Alien::Build's `alien_build_ok` monkeypatches `${class}::dist_dir`, so dist_dir-derived accessors work under test (2026-06-11)
- `field $x :reader` requires Perl 5.40+; on the 5.38 floor declare explicit reader methods inside the class block (2026-06-11)
- An installed Protobuf dist's WKT auto-include is a no-op (share installs under auto/share/dist/Protobuf, not relative to Parser.pm) — add `File::ShareDir::dist_dir('Protobuf') . '/proto'` to include_paths explicitly (2026-06-12)
- An alienfile local-path override needs a NON-EMPTY stub download dir (else Extract::Directory dies "no files extracted") plus an `install_prop->{download_detail}{$path} = { protocol => 'file' }` entry so the digest stage accepts the trusted local fetch (2026-06-11)

## Testing
- Drive an in-memory Future to its value in a Test2 unit test with `$f->get` (synchronous) — `$loop->await($f)` returns the Future object itself, not its resolved value. Codebase idiom is `->get` (converter_data.t); grep existing tests for the await pattern before writing a helper (2026-06-13)
- Unit-testing a method that `await`s an `async` collaborator: the mock for that collaborator MUST return a Future (`Future->done($v)` / `Future->fail($e)`), not the bare value — a plain return dies with "Can't locate object method AWAIT_IS_READY via package <the returned value's class>" (2026-06-12)
- `prove t` is non-recursive by default; this repo's `sdk/.proverc` adds `--recurse` so subdirectory tests run under the documented command (2026-06-11)
- Test names must stay ASCII — Test2's TAP handle is not UTF-8 even though test files `use utf8` (2026-06-11)
- Test2::V1 bare `use` exports only `T2()`; use `T2->method` style per spec §12.1, and emulate `require_ok` with `eval { require M; 1 }` into a lexical (2026-06-10)
- Never pass an expression that can return the empty list (`eval {}`, FFI::Platypus::Record opaque accessors on NULL) directly as a T2 method argument — list-context collapse shifts the test name into the value slot (2026-06-11)
